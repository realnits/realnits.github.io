This post covers notes from the TryHackMe Introduction to SIEM room — understanding how Security Information and Event Management systems transform scattered logs into actionable security alerts.

### Log Sources

Every device in a network constantly generates logs that record activity. These logs serve as evidence trails for both troubleshooting and attack detection. They fall into two main categories.

#### Host-Centric Logs

These capture activity occurring **inside** a device — user login attempts, file access, process execution, registry modification, PowerShell execution. They're generated by Windows endpoints, Linux machines, servers, and workstations.

#### Network-Centric Logs

These capture **communication between systems** — SSH connections, FTP transfers, web traffic, VPN access, network file sharing. They come from firewalls, routers, and IDS/IPS.

### Problems Without SIEM

Without a centralized platform, you're dealing with too many log sources (hundreds of events per second), no single location to search, limited context since individual logs don't tell the full attack story, impossible manual analysis at scale, and different log formats across every system. SIEM — Security Information and Event Management — solves all of this by collecting, standardizing, correlating, and analyzing logs from across the organization to detect threats.

### Core Features of SIEM

#### Centralized Log Collection

Collects logs from endpoints, servers, firewalls, and more using agents, APIs, or standard protocols. Everything flows to one place.

#### Log Parsing and Normalization

**Parsing** breaks logs into readable fields. **Normalization** converts all logs into a consistent format regardless of source. This is what makes cross-source correlation possible.

#### Correlation

This is where the real value lives. Correlation combines events from multiple sources to detect patterns that no single log could reveal. For example: VPN login from unusual IP → file access → PowerShell execution → outbound connection. Individually, each event might look benign. Together, they paint a picture of possible data exfiltration.

#### Real-Time Alerting

Detection rules trigger alerts that analysts investigate directly inside the SIEM. No more digging through raw logs.

#### Dashboards and Reporting

Summarized insights at a glance: failed logins, triggered rules, top domains, alerts overview, system health.

### Common Log Sources

**Windows** logs are viewed in Event Viewer. Each activity has an Event ID and logs are forwarded to SIEM for centralized analysis.

**Linux** stores logs in standard locations:
- `/var/log/auth.log` — authentication
- `/var/log/cron` — scheduled tasks
- `/var/log/httpd` — web activity
- `/var/log/kern` — kernel events

**Web Servers** track requests and responses, making them useful for detecting web attacks. Apache logs live in `/var/log/apache` or `/var/log/httpd`.

### Log Ingestion Methods

| Method | Description |
|------|------|
| Agent / Forwarder | Installed on host, sends logs |
| Syslog | Standard logging protocol |
| Manual Upload | Import offline logs |
| Port Forwarding | Send logs to listening SIEM port |

### Detection Rules

Rules are the core of any SIEM — they define the conditions that trigger alerts.

#### Example Conditions

- 5 failed logins in 10 seconds
- Successful login immediately after failures
- USB device inserted on a server
- Large outbound data transfer (potential exfiltration)

#### Example Rule Creation

**Case 1 — Log deletion:** Trigger on Event ID 104 (logs cleared). Any time this fires, it generates an alert.

**Case 2 — Suspicious command:** Trigger on Event ID 4688 (process execution) where the process name contains `whoami`. This catches reconnaissance activity.

### Alert Investigation Workflow

Once an alert triggers, the investigation follows a straightforward pattern:

1. Review the related events
2. Check the rule conditions that triggered the alert
3. Make a verdict

From there, you take action. If it's a **false positive**, tune the rule so it doesn't fire unnecessarily. If it's a **true positive**, dig deeper — contact the asset owner, isolate the infected host, block the malicious IP, and begin your incident response process.

The bottom line: SIEM transforms massive, scattered logs into correlated alerts, enabling analysts to detect and respond to attacks efficiently rather than drowning in raw data.
